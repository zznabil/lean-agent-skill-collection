# Organization-scale governance frameworks

## Task and boundary
- Evaluate whether an organisational governance framework is actually required for a named programme.
- Do not turn generic governance, maturity, audit or certification frameworks into default agent instructions.
- Work only on the selected artifact or assessment. This routine does not grant permission to run attacks, deploy, publish or change
  policy.
- OFF-DEFAULT GUARD: use only for the stated selection or review request; do not install as an always-on workflow.

## Source and limits
- Read [SOURCES.md](SOURCES.md) for the selected edition, official files, source boundaries and copying terms.
- Read the relevant source sections before making a source-specific decision. A compact routine is not the complete specification.
- Historical adoption decision: Reject globally. Keep this boundary unless an authorised decision explicitly changes it.

## Procedure
1. Read the register decision: organisation-scale governance is rejected globally.
2. Identify the concrete organisational requirement, sponsor, scope and decision authority.
3. If the requirement is absent, retain the exclusion and perform the task's existing contract instead.
4. If a programme is authorised, identify the exact framework, edition, authorised source and applicability rationale.
5. Separate governance policies, management-system processes and product-level technical controls.
6. Map responsibilities and evidence to the organisation rather than asking one agent to impersonate a complete governance system.
7. Identify costs, data collection, access changes and operational obligations before adoption.
8. Require explicit approval for any new persistent process, external service or account setting.
9. Keep implementation, assessment and certification decisions distinct and assigned to appropriate owners.
10. Return a scoped adoption or deferral recommendation without changing global Lean policy or inventing a canonical PDF.

## Preserve and verify
- Preserve facts, identifiers, links, required checks, permissions, negation, exceptions and failure/recovery paths.
- Separate planned work, actual evidence and unknown results. Missing or stale evidence is not a pass.
- Do not delete requirements to improve a score or satisfy the line budget; record an unresolved source or task conflict.
- Use the smallest check that can detect the relevant defect. A schema, linter or inventory alone does not prove task success.

## Worked case — authored, not an executed model result
- **Situation:** A repository refactor automatically adds an organisation-wide certification programme.
- **Expected:** Reject the scope expansion and request the actual organisational requirement before proposing programme work.
- **Missing-evidence case:** No specific framework, sponsor or implementation authority is identified.

## Finish and stop
- Return the scoped result, evidence, unresolved requirements and next permitted action.
- Make one correction pass and recheck affected evidence. If a required issue remains, report it rather than looping or claiming
  completion.
- Identify the checked scope, source edition, evidence and limits. Do not claim formal conformance or model-behaviour improvement
  from this routine.
