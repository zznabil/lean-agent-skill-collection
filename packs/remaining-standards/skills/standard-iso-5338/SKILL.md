# ISO/IEC 5338 AI lifecycle

## Communication kernel
If trusted root `AGENTS.md` loads, follow it; otherwise apply this standalone fallback. Do not claim root activation without evidence.
- **Brevity:** Use the fewest words that complete the task. Start with the answer, result or blocker. Remove filler, repeated conclusions, routine narration and decorative headings. Do not add a **Summary** heading or closing **TL;DR**. Use a leading **TL;DR** only when it improves a complex answer.
- **Language:** Use ASD-STE100-inspired short, active sentences and concrete verbs.
- **Terms:** Use ISO 704-inspired consistent terms: one preferred term per distinct concept. Define unfamiliar terms when needed; preserve exact technical and UI strings.
- **Structure:** Use Diátaxis to separate how-to, reference, explanation and tutorial content only when this helps navigation.
- **Integrity:** Preserve facts, actors, conditions, negation, exceptions, permissions, requirements, source rights, uncertainty, evidence, accessibility and the requested voice or format. Do not omit required details just to shorten text.
- **Safety and proof:** Use BCP 14 force only for normative rules. Keep warning-before-hazard, verified safe state, hold points, expected results, failure signs and recovery when relevant. Report actual test outcomes; do not invent a pass.
These are writing guides, not proof of standards conformance or host behaviour. Task-specific source rules still apply.
## Conditional execution rules
- For normative requirements, use BCP 14 (RFC 2119/8174) uppercase MUST, MUST NOT, SHOULD, SHOULD NOT and MAY without changing force. State one actor, action and observable verification target.
- For critical or risky work only, put warnings before hazards and hold points before critical or irreversible steps. Verify actual state before destructive or hazardous work.
- When failure is plausible, state the expected result, failure sign and recovery.
- Explain difficult mechanisms from simple foundations. Contrast noncompliant and compliant code or configuration when useful.
- For critical procedures, keep prerequisites, warnings, verified holds, actions, expected results and recovery; add headings only when useful.
- Give progress only when requested or useful. Keep progress distinct from the verdict.

## Task and boundary
- Plan or review lifecycle work for a named AI system under requirements selected by the project.
- Do not use an AI lifecycle template as proof of model quality. Do not replace the project's established lifecycle without approval.
- Work only on the selected artifact or assessment. This routine gives no permission to run attacks, deploy, publish or change policy.

## Procedure
1. Identify the AI-system boundary, stakeholders and lifecycle stage. Identify its relationship to existing system/software processes.
2. Record intended use, affected people, operational context and selected process obligations.
3. Trace relevant data acquisition, preparation, model development, integration and evaluation activities.
4. Assign responsibility for models, datasets, infrastructure and third-party components.
5. Plan transition, operation, monitoring, maintenance, change and retirement when they are in scope.
6. Define evidence and decision points for material changes to data, models, configuration or intended use.
7. Distinguish training success, evaluation success and operational acceptance.
8. Connect risk, security, privacy and human-oversight responsibilities to the relevant lifecycle activity.
9. Record residual gaps and re-evaluation triggers. Do not declare the lifecycle complete at deployment.
10. Use the licensed ISO/IEC 5338 source for formal process requirements. These steps provide Lean application guidance.

## Verify and recover
- **Worked check (illustrative, not executed):** A retrained model replaces the evaluated model without a new acceptance decision.
- **Expected:** Record the changed model and affected evidence, then complete the required re-evaluation before acceptance.
- **If blocked:** If the deployed model, data revision or lifecycle owner is unknown, stop the affected assessment or action. Record the missing prerequisite and request it from the responsible owner. Continue only independent, authorised work.
- Preserve facts, identifiers, links, required checks, permissions, negation, exceptions and failure/recovery paths.
- Distinguish planned work, actual evidence and unknown results. Missing or stale evidence is not a pass.
- Do not remove requirements to improve a score or meet the line budget. Record any unresolved source or task conflict.
- Use the smallest check that can detect the relevant defect. A schema, linter or inventory alone does not prove task success.

## Finish and stop
- Return the scoped result, evidence, unresolved requirements and next permitted action.
- Make one correction pass. Recheck affected evidence. If a required issue remains, report it. Do not loop or claim completion.
- Identify the checked scope, source edition, evidence and limits. Do not claim formal conformance or model-behaviour improvement from this routine.
