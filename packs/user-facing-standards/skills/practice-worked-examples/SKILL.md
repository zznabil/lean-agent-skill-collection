# Worked examples and self-explanation

## Use
- Use this skill when learners must understand and perform an unfamiliar procedure, not look up a single fact. Return a correct example and the next useful practice step.
- First identify the learning goal, prerequisite knowledge and difficult step.

## Source and scope
- Read the worked-example and explanatory-question sections in references/ies-organizing-instruction-2007.pdf.
- The research guide supports this teaching pattern. The pattern is not a separate formally published standard.
- Lean’s guided-to-independent sequence is an application choice. Select it from observed learner needs.

## Procedure
1. Select a small example that represents the intended procedure. State its starting facts and goal.
2. Show the steps in their valid order. Include each necessary condition or exception at its decision point.
3. Explain why the key step works. Connect the operation to the relevant principle instead of repeating the command.
4. When learner participation is part of the task, ask one focused self-explanation question about that step.
5. Inspect the answer or attempt. Address the specific mistaken idea before you add material.
6. Alternate example study with a related problem that the learner works on. Give a cue when current evidence warrants it.
7. Reduce cues after guided performance improves. Check independent transfer with a related new case, not a repeat of the example.
8. State the example’s limits explicitly. Help the learner avoid applying it when its prerequisites fail.

## Keep the task contract
- Do not present an invented example result as executed or experimentally verified.
- Do not remove an exception from the general rule because the example does not exercise it.
- An agent instruction can include a worked execution example. This does not require a quiz for the human user.
- Do not treat a copied answer, agreement or confidence statement as evidence of independent understanding.

## Verify and deliver
- Use relevant task evidence to verify the example’s calculation, commands and result.
- Separate example-following, guided performance and independent transfer.
- Return the example and only the next useful exercise. State untested cases and misunderstandings explicitly.

## Worked distinction
A learner copies the subnet mask from the example but cannot explain which bits changed.
Target that step with an explanation and a related case instead of declaring mastery from the copied answer.

## Communication kernel
If trusted root `AGENTS.md` is loaded, its policy governs. Otherwise apply this standalone kernel. If root `AGENTS.md` is loaded, it governs. Do not claim root activation without evidence. Run this skill’s source-specific procedure only for its task, not for every reply.
- Use ASD-STE100-inspired short, active technical sentences. Use ISO 704-inspired stable concepts and terminology. Use Diátaxis organization to separate how-to, reference and explanation when helpful. These are the default communication drivers, not a claim of formal standards conformance.
- Start with the supported result and next action. Preserve facts, exact negation, actors, conditions, exceptions, rights, permissions, uncertainty, evidence and the requested format. Never call an unchecked result compliant or complete.
- When text is normative, preserve BCP 14 MUST/SHOULD/MAY force and exceptions. For important requirements, name one actor, action and observable check.
- Before a hazardous action, state the verified risk and give a warning. For critical steps, include a hold point and a safe-state check. When failure is plausible, state the expected result, failure sign and recovery. These rules do not replace task-specific controls.
- For measurable multi-step work, use a named 20-cell ASCII bar (# processed, - remaining). Calculate the floor percentage from durable counts. Keep the PASS/FAIL/BLOCKED verdict separate. Count a failed, blocked, skipped or untested item only after you classify it with evidence. If no total is defensible, report the phase, evidence and next action without a bar. This rule does not invoke manual wait-what.
- For a difficult mechanism, explain it from foundations. For code or configuration, contrast compliant and noncompliant cases only when useful. Do not force examples or sections on simple tasks.
