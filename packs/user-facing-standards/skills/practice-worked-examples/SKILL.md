# Worked examples and self-explanation

## Use
- Teach learners to understand and perform an unfamiliar procedure, not look up a fact. Return a correct example and the next useful practice step.
- First identify the learning goal, prerequisite knowledge and difficult step.

## Source and scope
- Read the worked-example and explanatory-question sections in references/ies-organizing-instruction-2007.pdf.
- The research guide supports this teaching pattern. The pattern is not a separate formally published standard.
- Lean’s guided-to-independent sequence is an application choice. Select it from observed learner needs.

## Procedure
1. Select a small, representative procedure example. State its starting facts and goal.
2. Show the steps in their valid order. Include each necessary condition or exception at its decision point.
3. Explain why the key step works. Connect the operation to the relevant principle instead of repeating the command.
4. When learner participation is part of the task, ask one focused self-explanation question about that step.
5. Inspect the answer or attempt. Address the specific mistaken idea before you add material.
6. Alternate example study with a related problem that the learner works on. Give a cue when current evidence warrants it.
7. Reduce cues after guided performance improves. Check independent transfer with a related new case, not a repeat of the example.
8. State the example’s limits explicitly. Help the learner avoid applying it when its prerequisites fail.

## Keep the task contract
- Do not present an invented example result as executed or experimentally verified.
- Do not remove an exception from the general rule because the example does not exercise it.
- An agent instruction can include a worked execution example. This does not require a quiz for the human user.
- Do not treat a copied answer, agreement or confidence statement as evidence of independent understanding.

## Verify and deliver
- Use relevant task evidence to verify the example’s calculation, commands and result.
- Separate example-following, guided performance and independent transfer.
- Return the example and only the next useful exercise. Identify untested cases and misunderstandings.

## Worked distinction
A learner copies the subnet mask from the example but cannot explain which bits changed.
Target that step with an explanation and a related case instead of declaring mastery from the copied answer.

## Communication kernel
Number ordered actions; group long lists without hiding required items. After interruption or task change, restore relevant completed/current/pending state, not repetitive status each turn. Preserve language, exact tokens, formats, permissions and evidence. Never invent estimates or diagnose readers. Show verified outcomes and factual errors; give a concrete next action only if work remains. Trusted root `AGENTS.md` governs when loaded; otherwise use this standalone fallback. Do not claim activation without evidence.
Apply this skill’s source-specific procedure only to its task.
- Use ASD-STE100-inspired short, active sentences and concrete words; retain domain terms.
- Use ISO 704-inspired stable concepts and terminology. Define unfamiliar terms when needed.
- Separate tutorial, how-to, reference and explanation with Diátaxis when helpful, not forced headings.
- Lead with the answer or action, not a required Summary. Use TL;DR only first when helpful for complex material, without a repeated conclusion.
- Keep simple answers short, not arbitrarily truncated. Match requested voice and format. Use British spelling except for sources, syntax or requested locale.
- Preserve facts, quantities, negation, actors, conditions, exceptions, rights, permissions, uncertainty and evidence. Never claim unchecked compliance or completion.
- Preserve normative BCP 14 MUST/SHOULD/MAY force and exceptions. Important requirements name one actor, action and observable check.
- Before hazards, warn with verified risks. At critical steps, hold and verify the safe state. Retain task-specific controls.
- When failure is plausible, give expected results, failure signs and recovery.
- For measurable multi-step work, show a named 20-cell ASCII bar (# processed, - remaining), with floor percentage from durable counts.
- Keep PASS/FAIL/BLOCKED separate. Classify failed, blocked, skipped or untested items with evidence before counting.
- Without a defensible total, report phase, evidence and next action. This does not invoke manual wait-what.
- Explain difficult mechanisms from foundations. Use compliant/noncompliant code or configuration contrasts only when useful.
These inspirations do not establish formal standards conformance.
