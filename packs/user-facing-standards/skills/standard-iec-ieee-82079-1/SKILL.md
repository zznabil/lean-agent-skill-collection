# IEC/IEEE 82079-1: information for use

## Use
- Use this skill for product instructions, warnings and support information in relevant lifecycle activities. Provide information that supports the actual safe-use task.
- Draft, edit or review as requested. First read the target, product, intended users and authorised scope.

## Source and scope
- Use IEC/IEEE 82079-1:2019, Edition 2 as the target edition. See SOURCES.md for official access and source status.
- The author did not have the full licensed normative text when preparing this prototype. This skill does not bundle that text.
- This procedure applies Lean guidance to the published scope. It does not reproduce the standard’s clauses.
- For clause-level or conformance work, first obtain an authorised copy. Read the applicable clauses and exceptions. Without that copy, use only supported application guidance. Mark standard-specific requirements as unchecked.

## Procedure
1. Identify the product version, intended users, intended use, limits, environment and supported lifecycle activities.
2. Determine which information users need to install, operate, maintain, troubleshoot and retire the product, where applicable.
3. Use verified product hazards and authorised risk controls as the basis for safety information. Do not invent technical safety advice.
4. Place prerequisites, required competence and material warnings before the action they constrain.
5. Follow the sequence users must use. State each action, its target object, its expected result and available recovery.
6. Select delivery media, navigation and illustrations that users can access at the point of use.
7. Keep terminology, product identification, revisions and cross-references consistent with the actual product.
8. Have technical and information-design reviewers check consequential content against the current product.
9. Where practical, observe intended readers as they do the task. Correct missing information and wording that caused errors. Do not infer safe use from a readability score.
10. Assign an owner to maintain the information for use. Product changes must trigger review of the corresponding information.

## Keep the task contract
- Retain facts, quantities, terms, permissions, prohibitions, conditions, exceptions, warnings and required links.
- Do not invent requirements, numerical thresholds, clause numbers, user needs or evidence to make a checklist appear complete.
- A review or language edit gives no authority for execution, deployment, source acquisition fees or user-data collection.
- These human-oriented principles can inform agent instructions. They do not prove how an agent will interpret those instructions.

## Verify and deliver
- Check the actual task and a relevant failure or recovery path. Use evidence from intended users when available.
- Report source-verified clause findings separately from Lean design suggestions and unchecked items.
- Return the artifact or scoped findings first. State material limits and the evidence needed to resolve them.
- Do not claim formal conformance on the basis of this short routine, a readability score or an unexecuted review plan.

## Worked distinction
A maintenance guide lists a hazard only after the hazardous step.
Move the verified warning before that step without changing its technical content or required protective action.

## Communication kernel
If trusted root `AGENTS.md` loads, follow it; otherwise apply this standalone fallback. Do not claim root activation without evidence.
- **Brevity:** Use the fewest words that complete the task. Start with the answer, result or blocker. Remove filler, repeated conclusions, routine narration and decorative headings. Do not add a **Summary** heading or closing **TL;DR**. Use a leading **TL;DR** only when it improves a complex answer.
- **Language:** Use ASD-STE100-inspired short, active sentences and concrete verbs.
- **Terms:** Use ISO 704-inspired consistent terms: one preferred term per distinct concept. Define unfamiliar terms when needed; preserve exact technical and UI strings.
- **Structure:** Use Diátaxis to separate how-to, reference, explanation and tutorial content only when this helps navigation.
- **Integrity:** Preserve facts, actors, conditions, negation, exceptions, permissions, requirements, source rights, uncertainty, evidence, accessibility and the requested voice or format. Do not omit required details just to shorten text.
- **Safety and proof:** Use BCP 14 force only for normative rules. Keep warning-before-hazard, verified safe state, hold points, expected results, failure signs and recovery when relevant. Report actual test outcomes; do not invent a pass.
