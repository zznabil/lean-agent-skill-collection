# ISO/IEC 23859: understandable UI text
## Use
- Use this skill for UI labels, embedded help or errors when their meaning depends on interaction context. Provide text that supports the visible decision and recovery.
- Draft, edit or review as requested. First read the rendered target, users, task and authorised scope.
## Source and scope
- Use ISO/IEC 23859:2023 as the target edition. See SOURCES.md for official access and source status.
- The authors did not have the full licensed normative text when they created this prototype. This skill does not bundle it.
- This procedure applies Lean guidance to the published scope. It does not reproduce the standard’s clauses.
- For clause-level or conformance work, first obtain an authorised copy. Read the applicable clauses and exceptions. Without that copy, use only supported application guidance. Mark standard-specific requirements as unchecked.
## Procedure
1. Identify the reader, screen, language, task and decision that the text must support.
2. Check what users can see and do at that point. Do not give an instruction that depends on hidden state.
3. Use concrete names for actions and objects. Use the product’s established terms and the audience’s supported vocabulary.
4. Label each control so that users can distinguish its action from nearby alternatives.
5. Put short guidance at the decision point. Show consequential details before commitment.
6. For an error, state the known problem and a permitted next action. State what happened to work or data.
7. During localisation, preserve negation, units, limits and qualifiers. Do not replace a promise with a shorter promise that has a different meaning.
8. Test the text where readers see it. Include a mistaken action and recovery. Record what readers understood and could do.
9. Revise the text to address observed misunderstandings. Do not base revisions only on author preference or a sentence-length score.
## Keep the task contract
- Keep all facts, quantities, terms, permissions, prohibitions, conditions, exceptions, warnings and required links.
- Do not invent requirements, numerical thresholds, clause numbers, user needs or evidence to make a checklist appear complete.
- A review or language edit does not authorise execution, deployment, source acquisition fees or user-data collection.
- These principles for human readers can inform agent instructions. They do not prove how an agent will interpret those instructions.
## Verify and deliver
- Check the actual task and a relevant failure or recovery path. Use intended-user evidence when it is available.
- Keep source-verified clause findings separate from Lean design suggestions and unchecked items.
- Return the artifact or scoped findings first. State material limits and the evidence needed to resolve them.
- Do not claim formal conformance based on this short procedure, a readability score or a review plan that was not executed.
## Worked distinction
A confirmation button says "OK" after a permanent-delete question.
Label the action explicitly and keep the warning. Do not change the operation without stating the change.
## Communication kernel
If trusted root `AGENTS.md` is loaded, its policy governs. Otherwise apply this standalone kernel. If root `AGENTS.md` loads, it governs. Do not claim root activation without evidence. Run this skill’s source-specific procedure only for its task, not for every reply. These are inspired practices, not a claim of formal standards conformance.
- Use ASD-STE100-inspired short, active technical sentences. Use familiar words. Lead with the supported result and next action.
- Use ISO 704-inspired stable concepts and terminology. Keep terms consistent and preserve distinctions.
- Use Diátaxis organization when it helps. Separate how-to, reference and explanation. Do not force examples or sections on simple tasks.
- Preserve facts, exact negation, actors, conditions, exceptions, rights, permissions, uncertainty, evidence and the requested format. Never call an unchecked result compliant or complete.
- In normative text, preserve BCP 14 MUST/SHOULD/MAY force and exceptions. For important requirements, identify one actor, an action and an observable check.
- Before a hazardous action, show the verified risk and a warning. For critical steps, use a hold point and check the safe state. When failure is plausible, state the expected result, failure sign and recovery. These controls do not replace task-specific controls.
- For measurable multi-step work, use a named 20-cell ASCII bar (# processed, - remaining). Calculate the floor percentage from durable counts. Keep the PASS/FAIL/BLOCKED verdict separate. Count a failed, blocked, skipped or untested item only after classification with evidence. If no defensible total exists, report the phase, evidence and next action without a bar. This does not invoke manual wait-what.
- For a difficult mechanism, explain its foundations. For code or configuration, use a compliant/noncompliant contrast only when useful.
