# ISO/IEC 23859: understandable UI text
## Use
- Draft, edit or review UI labels, embedded help or errors whose meaning depends on interaction context. Support the visible decision and recovery.
- First read the rendered target, users, task and authorised scope.
## Source and scope
- Use ISO/IEC 23859:2023 as the target edition. See SOURCES.md for official access and source status.
- The authors did not have the full licensed normative text when they created this prototype. This skill does not bundle it.
- This procedure applies Lean guidance to the published scope. It does not reproduce the standard’s clauses.
- For clause-level or conformance work, first obtain an authorised copy. Read the applicable clauses and exceptions. Without that copy, use only supported application guidance. Mark standard-specific requirements as unchecked.
## Procedure
1. Identify the reader, screen, language, task and decision that the text must support.
2. Check what users can see and do at that point. Do not give an instruction that depends on hidden state.
3. Use concrete names for actions and objects. Use the product’s established terms and the audience’s supported vocabulary.
4. Label each control so that users can distinguish its action from nearby alternatives.
5. Put short guidance at the decision point. Show consequential details before commitment.
6. For an error, state the known problem and a permitted next action. State what happened to work or data.
7. During localisation, preserve negation, units, limits, qualifiers and promises. Do not shorten a promise by changing its meaning.
8. Test the text where readers see it. Include a mistaken action and recovery. Record what readers understood and could do.
9. Revise the text to address observed misunderstandings. Do not base revisions only on author preference or a sentence-length score.
## Keep the task contract
- Keep all facts, quantities, terms, permissions, prohibitions, conditions, exceptions, warnings and required links.
- Do not invent requirements, numerical thresholds, clause numbers, user needs or evidence to make a checklist appear complete.
- A review or language edit does not authorise execution, deployment, source acquisition fees or user-data collection.
- These principles for human readers can inform agent instructions. They do not prove how an agent will interpret those instructions.
## Verify and deliver
- Check the actual task and a relevant failure or recovery path. Use intended-user evidence when it is available.
- Keep source-verified clause findings separate from Lean design suggestions and unchecked items.
- Return the artefact or scoped findings first. State material limits and the evidence needed to resolve them.
- Do not claim formal conformance from this procedure, a readability score or an unexecuted review plan.
## Worked distinction
A confirmation button says "OK" after a permanent-delete question.
Label the action explicitly and keep the warning. Do not change the operation without stating the change.
## Communication kernel
Number ordered actions; group long lists without hiding required items. After interruption or task change, restore relevant completed/current/pending state, not repetitive status each turn. Preserve language, exact tokens, formats, permissions and evidence. Never invent estimates or diagnose readers. Show verified outcomes and factual errors; give a concrete next action only if work remains. Trusted root `AGENTS.md` governs when loaded; otherwise use this standalone fallback. Do not claim activation without evidence.
Apply this skill’s source-specific procedure only to its task.
- Use ASD-STE100-inspired short, active sentences and concrete words; retain domain terms.
- Use ISO 704-inspired stable concepts and terminology. Define unfamiliar terms when needed.
- Separate tutorial, how-to, reference and explanation with Diátaxis when helpful, not forced headings.
- Lead with the answer or action, not a required Summary. Use TL;DR only first when helpful for complex material, without a repeated conclusion.
- Keep simple answers short, not arbitrarily truncated. Match requested voice and format. Use British spelling except for sources, syntax or requested locale.
- Preserve facts, quantities, negation, actors, conditions, exceptions, rights, permissions, uncertainty and evidence. Never claim unchecked compliance or completion.
- Preserve normative BCP 14 MUST/SHOULD/MAY force and exceptions. Important requirements name one actor, action and observable check.
- Before hazards, warn with verified risks. At critical steps, hold and verify the safe state. Retain task-specific controls.
- When failure is plausible, give expected results, failure signs and recovery.
- For measurable multi-step work, show a named 20-cell ASCII bar (# processed, - remaining), with floor percentage from durable counts.
- Keep PASS/FAIL/BLOCKED separate. Classify failed, blocked, skipped or untested items with evidence before counting.
- Without a defensible total, report phase, evidence and next action. This does not invoke manual wait-what.
- Explain difficult mechanisms from foundations. Use compliant/noncompliant code or configuration contrasts only when useful.
These inspirations do not establish formal standards conformance.
