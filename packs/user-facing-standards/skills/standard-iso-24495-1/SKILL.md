# ISO 24495-1: plain-language usability
## Use
- Use this skill for a selected plain-language task when defined readers must find, understand and use information. Provide the revised artifact or scoped findings.
- Draft, edit or review as requested. First read the target, readers, task and authorised scope. Do not apply this procedure to every reply by default.
## Source and scope
- Use ISO 24495-1:2023 as the target edition. See SOURCES.md for official access and source status.
- The authors did not have the full licensed normative text when they created this prototype. This skill does not bundle it.
- This procedure applies Lean guidance to the published scope. It does not reproduce the standard’s clauses.
- For clause-level or conformance work, first obtain an authorised copy. Read the applicable clauses and exceptions. Without that copy, use only supported application guidance. Mark standard-specific requirements as unchecked.
## Procedure
1. Identify the primary reader and what that reader already knows. Identify the action or decision that the text must support.
2. Select information relevant to that need. Remove a digression only if it carries no required meaning.
3. Help readers find required information. Use an informative title, meaningful headings and a visible task order.
4. Put the main answer or action early. Do not move a prerequisite or warning after its commitment point.
5. Use familiar, concrete language and consistent terms. Explain each necessary specialised term at first use.
6. State who acts and what changes. Resolve vague pronouns from the source. If the source does not identify a referent, flag the gap.
7. Divide dense passages into coherent units. Keep conditions and exceptions with their rules.
8. Make the information usable. Include available prerequisites, the action, the expected result and safe recovery.
9. When reader evaluation is in scope, ask intended readers to find, explain and use the text. Revise the text to address observed barriers, not just to change the word count.
## Keep the task contract
- Keep all facts, quantities, terms, permissions, prohibitions, conditions, exceptions, warnings and required links.
- Do not invent requirements, numerical thresholds, clause numbers, user needs or evidence to make a checklist appear complete.
- A review or language edit does not authorise execution, deployment, source acquisition fees or user-data collection.
- These principles for human readers can inform agent instructions. They do not prove how an agent will interpret those instructions.
## Verify and deliver
- Check the actual task and a relevant failure or recovery path. Use intended-user evidence when it is available.
- Keep source-verified clause findings separate from Lean design suggestions and unchecked items.
- Return the artifact or scoped findings first. State material limits and the evidence needed to resolve them.
- Do not claim formal conformance based on this short procedure, a readability score or a review plan that was not executed.
## Worked distinction
A short instruction omits where a recovery file must be stored.
Use the source to restore the location. A brief instruction must still support a usable action.
## Communication kernel
If trusted root `AGENTS.md` loads, follow it; otherwise apply this standalone fallback. Do not claim root activation without evidence.
- **Brevity:** Use the fewest words that complete the task. Start with the answer, result or blocker. Remove filler, repeated conclusions, routine narration and decorative headings. Do not add a **Summary** heading or closing **TL;DR**. Use a leading **TL;DR** only when it improves a complex answer.
- **Language:** Use ASD-STE100-inspired short, active sentences and concrete verbs.
- **Terms:** Use ISO 704-inspired consistent terms: one preferred term per distinct concept. Define unfamiliar terms when needed; preserve exact technical and UI strings.
- **Structure:** Use Diátaxis to separate how-to, reference, explanation and tutorial content only when this helps navigation.
- **Integrity:** Preserve facts, actors, conditions, negation, exceptions, permissions, requirements, source rights, uncertainty, evidence, accessibility and the requested voice or format. Do not omit required details just to shorten text.
- **Safety and proof:** Use BCP 14 force only for normative rules. Keep warning-before-hazard, verified safe state, hold points, expected results, failure signs and recovery when relevant. Report actual test outcomes; do not invent a pass.
These are writing guides, not proof of standards conformance or host behaviour. Task-specific source rules still apply.
