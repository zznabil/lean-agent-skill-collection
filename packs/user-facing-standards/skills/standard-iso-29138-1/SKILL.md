# ISO/IEC 29138-1: identify accessibility needs

## Use
- Identify accessibility needs before you select ICT solutions. Deliver a needs map that records barriers, task outcomes, evidence and gaps.
- Draft, edit or review as requested. First read the task, users, environment and authorised scope.

## Source and scope
- Use ISO/IEC 29138-1:2018 as the target edition. See SOURCES.md for official access and source status.
- The full licensed normative text was unavailable when the authors prepared this prototype. This skill does not bundle that text.
- This procedure applies Lean guidance to the published scope. It does not reproduce the standard’s clauses.
- Before clause-level or conformance work, obtain an authorised copy. Read the applicable clauses and exceptions. Without that copy, use only supported application guidance. Mark standard-specific requirements as unchecked.

## Procedure
1. State the user task, environment, equipment and intended range of users.
2. Gather available evidence of user needs. Do not require unnecessary diagnosis or personal data.
3. Record each user capability or access need, its barrier and the task outcome that the barrier obstructs.
4. When the task requires a full mapping, use the authorised needs catalogue to check for missing need categories.
5. Distinguish a user need from a proposed feature, assistive technology or implementation technique.
6. Record context that changes the need. This includes available input, perception, understanding or communication.
7. Identify differing or conflicting needs. Seek representative input instead of silently selecting one default user.
8. Assign each supported need a stable local identifier and an evidence source. Do not invent an ISO item identifier.
9. For requirements or design work, provide each need, its affected task, evidence and verification question. Show unresolved gaps.

## Keep the task contract
- Retain facts, quantities, terms, permissions, prohibitions, conditions, exceptions, warnings and required links.
- Do not invent requirements, numerical thresholds, clause numbers, user needs or evidence to make a checklist appear complete.
- A review or language edit gives no authority to execute, deploy, incur source acquisition fees or collect user data.
- These human-oriented principles can inform agent instructions. They do not prove how an agent will interpret those instructions.

## Verify and deliver
- Check the actual task and a relevant failure or recovery path. Use evidence from intended users when available.
- Distinguish source-verified clause findings, Lean design suggestions and unchecked items.
- Return the artifact or scoped findings first. State material limits and the evidence needed to resolve them.
- Do not claim formal conformance based on this short procedure, a readability score or a review plan that has not been executed.

## Worked distinction
"Add a screen reader" proposes a solution. It does not fully state a user need.
Describe the information and task that a supported non-visual path must make available.

## Communication kernel
If trusted root `AGENTS.md` loads, follow it; otherwise apply this standalone fallback. Do not claim root activation without evidence.
- **Brevity:** Use the fewest words that complete the task. Start with the answer, result or blocker. Remove filler, repeated conclusions, routine narration and decorative headings. Do not add a **Summary** heading or closing **TL;DR**. Use a leading **TL;DR** only when it improves a complex answer.
- **Language:** Use ASD-STE100-inspired short, active sentences and concrete verbs.
- **Terms:** Use ISO 704-inspired consistent terms: one preferred term per distinct concept. Define unfamiliar terms when needed; preserve exact technical and UI strings.
- **Structure:** Use Diátaxis to separate how-to, reference, explanation and tutorial content only when this helps navigation.
- **Integrity:** Preserve facts, actors, conditions, negation, exceptions, permissions, requirements, source rights, uncertainty, evidence, accessibility and the requested voice or format. Do not omit required details just to shorten text.
- **Safety and proof:** Use BCP 14 force only for normative rules. Keep warning-before-hazard, verified safe state, hold points, expected results, failure signs and recovery when relevant. Report actual test outcomes; do not invent a pass.
These are writing guides, not proof of standards conformance or host behaviour. Task-specific source rules still apply.
## Conditional execution rules
- When editing normative text, retain BCP 14 MUST/SHOULD/MAY force and exceptions. For important requirements, identify one actor, an action and an observable check.
- Before a hazardous action, state the verified risk and give a warning. For critical steps, use a hold point and check the safe state. When failure is plausible, give the expected result, failure sign and recovery. These rules do not replace task-specific controls.
- Give progress only when requested or useful. Keep progress distinct from the verdict.
- For a difficult mechanism, explain it from foundations. For code or configuration, contrast compliant and noncompliant forms only when useful.
