# ISO 704: concept and terminology control
## Use
- Use this routine when technical terms or definitions conflict in a document, interface or agent policy. Deliver a consistent concept-to-term decision within the authorised scope.
- Draft, edit or review as requested. First read the target, readers, task and established terminology. Do not change terms for variety.
## Source and scope
- Target edition: ISO 704:2022, Edition 4. See SOURCES.md for official access and source status.
- The author did not have the full licensed normative text when authoring this prototype. This collection does not bundle that text.
- This procedure applies Lean guidance to the published scope. It does not reproduce the standard’s clauses.
- For clause-level or conformance work, first obtain an authorised copy. Read the applicable clauses and exceptions. Without that copy, use only supported application guidance. Mark standard-specific requirements as unchecked.
## Procedure
1. Define the subject field, scope, audience and authoritative terminology sources.
2. Identify the concept behind each disputed term before you replace words.
3. Compare concept characteristics and relationships. Distinguish genuine synonyms from different operations.
4. Select one preferred designation for each concept within the defined scope. Record permitted variants.
5. Write a useful definition that distinguishes the concept. Avoid circular wording and unsupported characteristics.
6. Store the term, definition, abbreviation, context and source together in a small terminology record.
7. Expand an unfamiliar abbreviation at its first relevant use. Preserve exact identifiers and mandated labels.
8. Apply the selected term consistently to prose, examples, UI labels and related documents within the authorised scope.
9. Refer unresolved concept conflicts to the domain expert or source owner. Do not publish a term change that silently merges different operations.
## Keep the task contract
- Retain facts, quantities, terms, permissions, prohibitions, conditions, exceptions, warnings and required links.
- Do not invent requirements, numerical thresholds, clause numbers, user needs or evidence to make a checklist appear complete.
- A review or language edit does not authorise execution, deployment, source acquisition fees or user-data collection.
- These human-oriented principles can inform agent instructions. They do not prove how an agent will interpret those instructions.
## Verify and deliver
- Check the actual task and a relevant failure or recovery path. Use intended-user evidence when available.
- Report source-verified clause findings separately from Lean design suggestions and unchecked items.
- Return the artifact or scoped findings first. State material limits and the evidence needed to resolve them.
- Do not claim formal conformance based on this short routine, a readability score or a review plan that you have not executed.
## Worked distinction
The project uses verification for checking specified requirements and validation for intended-use fitness.
Do not merge the two words merely to reduce vocabulary. First determine whether the concepts are identical.
## Communication kernel
If trusted root `AGENTS.md` loads, follow it; otherwise apply this standalone fallback. Do not claim root activation without evidence.
- **Brevity:** Use the fewest words that complete the task. Start with the answer, result or blocker. Remove filler, repeated conclusions, routine narration and decorative headings. Do not add a **Summary** heading or closing **TL;DR**. Use a leading **TL;DR** only when it improves a complex answer.
- **Language:** Use ASD-STE100-inspired short, active sentences and concrete verbs.
- **Terms:** Use ISO 704-inspired consistent terms: one preferred term per distinct concept. Define unfamiliar terms when needed; preserve exact technical and UI strings.
- **Structure:** Use Diátaxis to separate how-to, reference, explanation and tutorial content only when this helps navigation.
- **Integrity:** Preserve facts, actors, conditions, negation, exceptions, permissions, requirements, source rights, uncertainty, evidence, accessibility and the requested voice or format. Do not omit required details just to shorten text.
- **Safety and proof:** Use BCP 14 force only for normative rules. Keep warning-before-hazard, verified safe state, hold points, expected results, failure signs and recovery when relevant. Report actual test outcomes; do not invent a pass.
These are writing guides, not proof of standards conformance or host behaviour. Task-specific source rules still apply.
