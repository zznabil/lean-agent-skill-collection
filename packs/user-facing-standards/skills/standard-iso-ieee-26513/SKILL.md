# ISO/IEC/IEEE 26513: review user information

## Use
- Use this skill to plan or perform an information review for actual user tasks. Deliver findings linked to passages and evidence from rechecks.
- Draft, edit or review as requested. First read the delivered artifact and the information about users, product version and authorised scope.

## Source and scope
- Target edition: ISO/IEC/IEEE 26513:2017; successor at FDIS in checked catalogue. See SOURCES.md for official access and source status.
- The full licensed normative text was unavailable when this prototype was authored. It is not bundled.
- These steps apply Lean guidance to the published scope. They do not reproduce the standard’s clauses.
- For clause-level or conformance work, first obtain an authorised copy. Read the applicable clauses and exceptions. Without that copy, use only supported application guidance. Mark standard-specific requirements unchecked.

## Procedure
1. Identify the information revision, product revision, intended users, target tasks and review purpose.
2. Set review criteria. Distinguish technical accuracy, completeness, usability and accessibility.
3. Assign reviewers who have relevant domain and information expertise. Record independence where required.
4. Inspect the delivered medium. Include navigation, links, examples, warnings and recovery information.
5. To check technical accuracy, compare claims and procedures with authoritative product behaviour and requirements.
6. To check user performance, ask representative intended users to find information and attempt the task when authorised.
7. Record observed errors, assistance, missed prerequisites and recovery failures. Do not rely on stated preference.
8. Link each finding to the exact passage, task, evidence, impact and proposed correction.
9. Recheck corrections on the affected task. Record unresolved findings, excluded scope and the task outcome that remains uncertain.

## Keep the task contract
- Preserve facts, quantities, terms, permissions, prohibitions, conditions, exceptions, warnings and required links.
- Do not invent requirements, numerical thresholds, clause numbers, user needs or evidence to make a checklist appear complete.
- A review or language edit does not authorise execution, deployment, source acquisition fees or user-data collection.
- These human-oriented principles can inform agent instructions. They do not prove how an agent will interpret those instructions.

## Verify and deliver
- Check the actual task and a relevant failure or recovery path. Use intended-user evidence when available.
- Distinguish source-verified clause findings, Lean design suggestions and unchecked items.
- Return the artifact or scoped findings first. State material limits and the evidence needed to resolve them.
- Do not claim formal conformance from this short routine, a readability score or an unexecuted review plan.

## Worked distinction
A reviewer approves a help page because its sentences are short.
Also test whether users can locate the prerequisite and complete the documented task.

## Communication kernel
If trusted root `AGENTS.md` loads, follow it; otherwise apply this standalone fallback. Do not claim root activation without evidence.
- **Brevity:** Use the fewest words that complete the task. Start with the answer, result or blocker. Remove filler, repeated conclusions, routine narration and decorative headings. Do not add a **Summary** heading or closing **TL;DR**. Use a leading **TL;DR** only when it improves a complex answer.
- **Language:** Use ASD-STE100-inspired short, active sentences and concrete verbs.
- **Terms:** Use ISO 704-inspired consistent terms: one preferred term per distinct concept. Define unfamiliar terms when needed; preserve exact technical and UI strings.
- **Structure:** Use Diátaxis to separate how-to, reference, explanation and tutorial content only when this helps navigation.
- **Integrity:** Preserve facts, actors, conditions, negation, exceptions, permissions, requirements, source rights, uncertainty, evidence, accessibility and the requested voice or format. Do not omit required details just to shorten text.
- **Safety and proof:** Use BCP 14 force only for normative rules. Keep warning-before-hazard, verified safe state, hold points, expected results, failure signs and recovery when relevant. Report actual test outcomes; do not invent a pass.
These are writing guides, not proof of standards conformance or host behaviour. Task-specific source rules still apply.
## Conditional execution rules
- When editing normative text, preserve BCP 14 MUST/SHOULD/MAY force and exceptions. For important requirements, name one actor, action and observable check.
- Before a hazardous action, state the verified risk and give a warning. For critical steps, use a hold point and check the safe state. When failure is plausible, give the expected result, failure sign and recovery. These controls do not replace task-specific controls.
- Give progress only when requested or useful. Keep progress distinct from the verdict.
- When explaining a difficult mechanism, start from foundations. For code or configuration, use a compliant/noncompliant contrast only when useful.
