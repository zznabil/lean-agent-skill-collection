# Review lanes

- **Requirements — ISO/IEC/IEEE 29148:** source-to-requirement traceability, task acceptance, standing Definition of Done, measurable checks, omitted behavior, scope drift, compatibility, unapproved reinterpretation, and the developer or operator contract: setup, commands, environment variables, default ports, feature gates, migrations, and version boundaries.
- **Proof integrity and acceptance gates:** stable outcome IDs; requirement-to-verifier mapping; direct observation of the named artifact or behavior; process-success plus success-only output when matching text; positive controls for absence tests; independent measurement of supplied numbers; sensitivity to a representative broken state; current re-execution rather than stored status; required abandonment or deferment not promoted to completion; and leaf-local versus branch-integration verifier placement.
- **Code correctness:** functional behavior, error paths, cleanup, types, data flow, dependencies, compatibility, observability, concurrency, and testability. Trace side effects through relevant callers and interfaces. Read tests and specification before treating implementation as the contract.
- **Maintainability/simplification:** use the priority correctness → safety → architecture → simplicity → diff size → lines of code; classify opportunities as delete, reuse, standard library, native platform, installed dependency, inline, consolidate, or shrink; inspect canonical ownership, explicit boundaries, special-case growth, duplicated policy, hidden coupling, unnecessary wrappers, dead code, narration comments, placeholders, unjustified type escapes, defensive branches with no real failure mode, and whether a smaller direct design preserves behavior. For an explicitly strict structural review, search for a reframing that removes concepts, branches, modes, wrappers, or state instead of redistributing them; recommend it only when contract preservation and migration cost are evidenced. A refactor must reduce net complexity rather than relocate it. File size is a signal to inspect, not a defect by itself. Suspected dead behavior defaults to keep until dynamic, reflective, external, and configuration consumers are disproved.
- **Interface and accessibility — WCAG 2.2, WAI-ARIA APG, ISO 9241-112:2025, ISO 9241-171:2025, ISO 21801-1, ISO/IEC 29138:** real screenshots and interaction; supplied-reference comparison; user accessibility need → barrier → requirement or journey → evidence; responsive layout; hierarchy; copy; loading, empty, error, focus, disabled, validation, persistence, interruption, orientation, memory burden, and recovery; realistic data; keyboard, focus, name, role, state, and visible outcome.
- **Human friction and stewardship:** avoidable user steps, repeated entry, surprising defaults, missing artifact or use path, unclear recovery, unnecessary approvals, hidden manual upkeep, and unclear ownership or handoff. Report only concrete human cost; do not turn personal preference into a blocker.
- **User information — IEC/IEEE 82079-1, ISO/IEC/IEEE 26514 and 26513, ISO/IEC 23859, ISO 704:** intended user, task, context, information need, findability, prerequisites, action sequence, expected result, recovery, consequences, stable terminology, layered detail, embedded UI text, and actual task evidence. Use CDC CCI or PEMAT-style checks only as diagnostics. An Easy-to-Read claim requires intended-user co-review.
- **Writing:** audience, purpose, structure, claims, citations, calculations, caveats, repetition, ambiguity, tone, unsupported certainty, and bidirectional source coverage.
- **Data/analysis — ISO/IEC 25012, ISO/IEC 25024, ISO/IEC 5259 when applicable:** source quality, joins, units, missing data, leakage, reproducibility, statistical method, charts, and conclusion fit.
- **Architecture — ISO/IEC/IEEE 42010, ATAM, ADR/MADR:** stakeholders, concerns, quality-attribute scenarios and trade-offs, boundaries, data ownership, trust boundaries, strict input normalization, canonical errors, machine-checkable HTTP or event contracts, cross-surface policy parity, success/failure/unknown outcomes, migration, rollback, operations, and speculative complexity.
- **Agent operability:** cold startup from documented instructions, canonical non-interactive commands, environment and secret boundaries, a fast validation loop, deterministic outputs, agent-readable errors, and whether documentation matches actual behavior. Tool-environment limitations are not repository defects.
- **Security, privacy, and supply chain:** protected assets, abuse cases, authorization, secrets, injection, file safety, least privilege, data purpose and minimization, access, retention and deletion, dependency ownership, provenance, lockfile and transitive changes, lifecycle scripts, and applicable ASVS or versioned AI-security requirements and threat cases.
- **Reliability and operations — Google SRE, OpenTelemetry, W3C Trace Context:** retries, idempotency, races, data integrity, recovery, user-facing SLI, target, window and error-budget action, structured logs, end-to-end correlation, bounded metrics, tracing, symptom alerts, runbooks, and rollback evidence.
- **Performance:** measured latency, throughput, memory, startup, network, or user-experience data under comparable conditions. Static findings are `potential impact`; inspect variance, correctness, and meaningful improvement before recommending complexity.
- **Agent/skill/workflow:** trigger precision, conflicts, unavailable tools, malformed input, prompt injection, tool permissions, sensitive data, state poisoning, context rollover, duplicate work, runaway loops, benchmark gaming, fabricated evidence, false completion, executable workflow trust, automatic updates, dynamic evaluation, resume determinism, child failure handling, barrier justification, structured boundaries, and silent caps. When traces exist, evaluate the end outcome, the full trajectory, and individual tool choices and arguments separately. Inspect the current AI asset card when available; material model, data, prompt, evaluator, tool, or deployment changes invalidate stale evidence. Use a concrete AI risk or security baseline when scope warrants it.
