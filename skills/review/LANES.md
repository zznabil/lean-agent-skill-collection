# Review lanes

- **Requirements — ISO/IEC/IEEE 29148:** Check source-to-requirement traceability, task acceptance, the standing Definition of Done, and measurable checks. Check omitted behavior, scope drift, compatibility, and unapproved reinterpretation. Check the developer or operator contract: setup, commands, environment variables, default ports, feature gates, migrations, and version boundaries.
- **Proof integrity and acceptance gates:** Check stable outcome IDs and requirement-to-verifier mapping. Require direct observation of the named artifact or behavior. For text matches, check process success and success-only output. For absence tests, check positive controls. Measure supplied numbers independently. Check verifier sensitivity to a representative broken state. Use current re-execution, not stored status. Do not promote required abandonment or deferment to completion. Check whether verifiers belong at the leaf-local or branch-integration level.
- **Code correctness:** Check functional behavior, error paths, cleanup, types, data flow, dependencies, compatibility, observability, concurrency, and testability. Trace side effects through relevant callers and interfaces. Read tests and the specification before treating the implementation as the contract.
- **Maintainability/simplification:** Apply this priority: correctness → safety → architecture → simplicity → diff size → lines of code. Classify opportunities as delete, reuse, standard library, native platform, installed dependency, inline, consolidate, or shrink. Inspect canonical ownership, explicit boundaries, special-case growth, duplicated policy, hidden coupling, unnecessary wrappers, dead code, narration comments, placeholders, unjustified type escapes, and defensive branches with no real failure mode. Check whether a smaller direct design preserves behavior. For an explicitly strict structural review, seek a design that removes concepts, branches, modes, wrappers, or state instead of redistributing them. Recommend that design only with evidence of contract preservation and migration cost. A refactor must reduce net complexity, not relocate it. Treat file size as an inspection signal, not a defect by itself. Keep suspected dead behavior by default until you disprove dynamic, reflective, external, and configuration consumers.
- **Interface and accessibility — WCAG 2.2, WAI-ARIA APG, ISO 9241-112:2025, ISO 9241-171:2025, ISO 21801-1, ISO/IEC 29138:** Inspect real screenshots and interaction. Compare supplied references. Trace user accessibility need → barrier → requirement or journey → evidence. Check responsive layout, hierarchy, copy, and realistic data. Check loading, empty, error, focus, disabled, validation, persistence, interruption, orientation, memory burden, and recovery. Check keyboard use, focus, name, role, state, and visible outcome.
- **Human friction and stewardship:** Check avoidable user steps, repeated entry, surprising defaults, missing artifacts or use paths, unclear recovery, unnecessary approvals, hidden manual upkeep, and unclear ownership or handoff. Report only concrete human cost. Do not make personal preference a blocker.
- **User information — IEC/IEEE 82079-1, ISO/IEC/IEEE 26514 and 26513, ISO/IEC 23859, ISO 704:** Check the intended user, task, context, information need, findability, prerequisites, action sequence, expected result, recovery, and consequences. Check stable terminology, layered detail, embedded UI text, and actual task evidence. Use CDC CCI or PEMAT-style checks only as diagnostics. Require intended-user co-review for an Easy-to-Read claim.
- **Writing:** Check audience, purpose, structure, claims, citations, calculations, caveats, repetition, ambiguity, tone, unsupported certainty, and bidirectional source coverage.
- **Data/analysis — ISO/IEC 25012, ISO/IEC 25024, ISO/IEC 5259 when applicable:** Check source quality, joins, units, missing data, leakage, reproducibility, statistical method, charts, and whether conclusions fit the evidence.
- **Architecture — ISO/IEC/IEEE 42010, ATAM, ADR/MADR:** Check stakeholders, concerns, quality-attribute scenarios and trade-offs, boundaries, data ownership, and trust boundaries. Check strict input normalization, canonical errors, machine-checkable HTTP or event contracts, and cross-surface policy parity. Check success/failure/unknown outcomes, migration, rollback, operations, and speculative complexity.
- **Agent operability:** Check cold startup from documented instructions, canonical non-interactive commands, environment and secret boundaries, a fast validation loop, deterministic outputs, and agent-readable errors. Check documentation against actual behavior. Do not classify tool-environment limitations as repository defects.
- **Security, privacy, and supply chain:** Check protected assets, abuse cases, authorization, secrets, injection, file safety, least privilege, data purpose and minimization, access, retention, and deletion. Check dependency ownership, provenance, lockfile and transitive changes, and lifecycle scripts. Check applicable ASVS or versioned AI-security requirements and threat cases.
- **Reliability and operations — Google SRE, OpenTelemetry, W3C Trace Context:** Check retries, idempotency, races, data integrity, and recovery. Check user-facing SLI, target, window, and error-budget action. Check structured logs, end-to-end correlation, bounded metrics, tracing, symptom alerts, runbooks, and rollback evidence.
- **Performance:** Check measured latency, throughput, memory, startup, network, or user-experience data under comparable conditions. Label static findings `potential impact`. Inspect variance, correctness, and meaningful improvement before recommending complexity.
- **Agent/skill/workflow:** Check trigger precision, conflicts, unavailable tools, malformed input, prompt injection, tool permissions, sensitive data, state poisoning, context rollover, duplicate work, runaway loops, benchmark gaming, fabricated evidence, and false completion. Check executable workflow trust, automatic updates, dynamic evaluation, resume determinism, child failure handling, barrier justification, structured boundaries, and silent caps. When traces exist, assess the end outcome, full trajectory, and individual tool choices and arguments separately. Inspect the current AI asset card when available. Material model, data, prompt, evaluator, tool, or deployment changes invalidate stale evidence. Use a concrete AI risk or security baseline when the scope warrants it.
