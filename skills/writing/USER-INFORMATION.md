# Human-usable information

Use for substantial instructions, manuals, onboarding, forms, UI text, errors or recovery help. Apply only what the user task needs; a simple answer does not need a manual.

Preserve factual and safety-critical meaning before stylistic simplicity. Never shorten away a warning, condition, exception or distinction that changes action or risk. These are independently summarised influences, not licensed normative text or a conformance claim.

## Task and audience

For substantial user instructions or help, identify audience and task; provide prerequisites, action, expected result, consequences and recovery, then review or test the actual task with intended users as risk warrants. (IEC/IEEE 82079-1; ISO/IEC/IEEE 26514; ISO/IEC/IEEE 26513).

Record relevant prior knowledge, context, medium and the decision the information supports. Keep required steps in the essential path; add guided examples or expert detail only when useful. Do not hide safety or recovery behind optional detail.

When an accessibility need affects a journey, trace need to barrier, requirement and observed evidence; do not assume one diagnosis describes all users. (ISO/IEC 29138-1; ISO/IEC 29138-4).

## Procedure and recovery

Use only the fields that help:

```text
Outcome
Before you start
Current state
Action
Expected result
If it did not work
Next
```

Keep each step to one main action or tightly coupled group. Put warnings, prerequisites, costs, irreversible effects and data-loss risk before commitment. An error should identify what happened, the safe next action, the state of the user's work and where to find necessary detail; do not blame the user or hide a known recovery behind a generic failure.

## Cognitive accessibility and terms

For UI text or cognitive-accessibility barriers, use concrete labels, visible task state, recoverable steps and resumable instructions; evaluate the rendered context and needed alternate representations. (ISO/IEC 23859; ISO 21801-1; ISO 9241-171).

Show what is complete, current and next, plus important prior choices. Expose information needed for the current decision rather than demanding recall from another screen. Use hierarchy, spacing and grouping to expose structure. Check resumption after distraction, navigation away or error, including whether work was preserved.

When naming concepts or controls, use one preferred term per concept within scope and explain unavoidable terminology at first use. (ISO 704).

## Specialised representations

Only when Easy-to-Read is requested or justified by the audience, use a dedicated representation and intended-user co-review; do not claim the rules or use the logo without the required proofreading and attribution. (Inclusion Europe Easy-to-Read).

Easy-to-Read is not a synonym for short prose. Keep access to fuller information when needed. Do not treat a readability formula as evidence of comprehension or accessibility.

## Evaluation

Observe the actual task: can intended users find the information, explain it correctly, complete the action and recover after interruption? Record missed warnings, wording-related errors, help needed and relevant differences between target users. Use independent review for consequential information; a tidy layout or successful save is not user testing.

For public or patient information within each tool's domain, use the appropriate diagnostic to inspect clarity and actionability; do not transfer domain scores into universal software release gates. (CDC Clear Communication Index; AHRQ PEMAT).

Use CDC CCI for applicable public communication concerns such as the main message, action, numbers and risk. Use PEMAT for the understandability and actionability of patient material. Record unavailable user evaluation as a limit, not a pass.
